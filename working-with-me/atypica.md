# atypica 这个项目

**这份文档是个示范。** 其他几份讲的是换个项目也成立的工作方式，这一份不是——它是我自己的项目上下文，放在这里是为了说明这类文档该写成什么样。你 fork 之后把它换成你自己的项目，或者直接删掉。

为什么需要这样一份文档：agent 接不住的往往不是技术，是名字。你嘴里那些天天说的词——某个核心概念、某个模块、某个产品形态——它没见过，一个词猜错，后面整条推理都跟着歪。所以把这些名字写下来，比写十条编码规范有用。

在别的项目里工作，跳过前面几节，但把最后一节"到一个新项目该先摸清什么"读一下，那部分是通用的。

---

## 我在这个项目里的角色

代码是我写的（Rust、TypeScript 都写），产品方向、合作、推广、预算、招人也是我在管。所以我扔给你的任务会横跨这些领域，一条消息里从数据库跳到定价策略是常态。

## 我嘴里的那些名字

我说话时直接用这些名字，不解释。听不懂就接不住：

- **atypica.AI**——主产品，AI 原生的市场研究平台。多个 agent 协作，模拟消费者、做访谈、出研究报告。
- **Study**——一次研究任务，产品的核心概念。执行研究的主 agent 叫 Study Agent。
- **Panel**——受访者的集合，用来跑访谈和调研。我自己判断过这个词用户听不懂，所以只在内部用。
- **Persona**——模拟出来的消费者个体。
- **Console**——研究执行过程的展示界面。
- **Prosumer / Enterprise**——两种产品形态，不是两个价格档：一种给个人专业用户，一种给企业。产品结构改过几轮，我嘴里可能还会冒出被替换掉的旧名字——听到不认识的名字先确认它对应现在的哪个，别自己猜。

写你自己那份时，照这个粒度来：**一个名字一行，说它是什么，必要时说它不是什么。** 不用写全，写那些你张口就说、外人一定听不懂的。

**还有一件事：我用语音输入。** 转写会出错，人名和产品名尤其容易被听成别的词，有时会冒出一个根本不存在的产品名。遇到一个名字在上下文里对不上，先怀疑是转写错误，问一句就好——不要当成一个新概念记下来，然后一路推理下去。那会让整段对话建立在一个不存在的东西上。

## 项目资料在哪

- **代码约定**：仓库根目录的 CLAUDE.md，以及它引用的几份文档（设计原则、代码约定、样式约定）。动手写代码前读完。
- **产品策略、叙事、目标、定价**：在我自己的笔记库里，不在代码仓库。要重想任何一页或一条叙事之前先问我要，别凭现有实现推。
- **其他 skill**：写图片 prompt 用 [atypica-visual-style](https://github.com/atypica-AI/atypica-visual-style-skill)；用我本人口吻写文章用 [xdvoice](https://github.com/web3nomad/xdvoice)。

## 到一个新项目该先摸清什么

这一节通用。换到任何项目，上面那些名字都不成立，但下面这个顺序成立：

1. **读项目自己的约定文档。** 根目录的 CLAUDE.md、README、CONTRIBUTING，以及它们引用的文件。这是最快知道"这个项目怎么写代码"的方式。
2. **读提交历史。** message 用什么语言、写多细、一个 commit 多大粒度，看前二十条就有答案。分支怎么命名、PR 正文写什么，同样看得出来。没有约定文档的项目（很常见），约定就写在这里。
3. **找一个同类的已有实现照着写。** 命名、错误处理、日志、目录归属，跟着旁边的代码。参照物要选对：同类的、最近写的，不要随手挑一个最老的。
4. **搞清楚这个项目的名词。** 每个项目有自己的核心概念，先弄明白它们分别指什么、边界在哪，再动手。用错一个概念，后面所有讨论都会歪。
5. **搞清楚日志和数据在哪看。** 出问题时查什么、怎么查，提前知道比事发时再问快得多。
