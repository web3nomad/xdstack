# atypica 这个项目

**这份文档是个示范。** 另外几份讲的是换个项目也成立的做事方式，这一份不是。它是我自己项目的背景，放在这里，是想说明这类文档该写成什么样。你 fork 之后，把它换成你自己的项目，或者直接删掉。

为什么要有这么一份：agent 接不住的往往不是技术，是名字。你天天挂在嘴上的词，比如某个核心概念、某个模块、某种产品形态，它没见过。一个词猜错，后面整条思路都跟着歪。所以把这些名字写下来，比写十条编码规范有用。

在别的项目里干活，前面几节可以跳过，但最后一节"到一个新项目该先摸清什么"要读，那部分哪里都用得上。

---

## 我在这个项目里的角色

代码是我写的，Rust、TypeScript 都写。产品方向、合作、推广、预算、招人也是我在管。所以我交给你的事会跨好几块，一条消息从数据库跳到定价，很正常。

## 我常说的那些名字

这些名字我张口就说，不会解释。听不懂就接不住：

- **atypica.AI**：主产品，一个用 AI 做市场研究的平台。多个 agent 一起干活：模拟消费者、做访谈、出研究报告。
- **Study**：一次研究任务，产品最核心的概念。执行研究的主 agent 叫 Study Agent。
- **Universal**：另一个 agent，后来照着 Study 写的，两套代码各管各的。我说 study 就只看 study，别顺着调用关系读到 Universal，再把两个混在一起讲。
- **Panel**：一组受访者，用来跑访谈和调研。我自己判断过用户看不懂这个词，所以只在内部说。
- **Persona**：模拟出来的一个消费者。
- **Console**：展示研究执行过程的界面。
- **Prosumer / Enterprise**：两种产品形态，不是两个价格档，一种给个人专业用户，一种给企业。产品结构改过几轮，我嘴里偶尔还会冒出被换掉的旧名字，听到不认识的，先问清楚对应现在的哪个，别自己猜。

写你自己那份时，照这个粗细来：**一个名字一行，说它是什么，有必要就说它不是什么。** 不用写全，写那些你张口就说、外人肯定听不懂的。

**还有一件事：我用语音输入。** 转写会出错，人名和产品名最容易被写成别的词，有时还会冒出一个根本不存在的产品名。一个名字在上下文里对不上，先想是不是转写错了，问一句就好。别把它当成新东西记下来，再顺着它往下推，那样整段对话都建在一个不存在的东西上。

## 项目资料在哪

- **代码约定**：仓库根目录的 CLAUDE.md，还有它引用的几份文档（设计原则、代码约定、样式约定、怎么给人讲清楚一件事）。写代码前读完。
- **产品策略、怎么讲这个产品、目标、定价**：在我自己的笔记库里，不在代码仓库。要重新想任何一页、任何一种讲法之前，先问我要，别从现有的实现往回推。
- **其他 skill**：写图片 prompt 用 [atypica-visual-style](https://github.com/atypica-AI/atypica-visual-style-skill)；用我本人的口吻写文章用 [xdvoice](https://github.com/web3nomad/xdvoice)。

## 到一个新项目该先摸清什么

这一节换到哪个项目都用得上。换了项目，上面那些名字都不算数了，但下面这几步还是这么走：

1. **读项目自己的约定文档。** 根目录的 CLAUDE.md、README、CONTRIBUTING，还有它们引用的文件。想知道这个项目怎么写代码，这是最快的办法。
2. **看提交历史。** commit message 用什么语言、写多细、一个 commit 改多少，看最近二十条就知道。分支怎么起名、PR 正文写什么，也看得出来。没有约定文档的项目很常见，那规矩就写在这里。
3. **找一个同类的现成实现，照着写。** 名字怎么起、错误怎么处理、日志怎么打、文件放哪一层，都跟着旁边的代码走。参照也要挑对：同类的、最近写的，别随手挑一个最老的。
4. **弄清楚这个项目的名词。** 每个项目都有自己的核心概念。先弄明白每个词指什么、管到哪为止，再动手。用错一个概念，后面的讨论全会跟着歪。
5. **弄清楚日志和数据在哪看。** 出了问题该查什么、怎么查，提前知道比出事时再问快得多。
