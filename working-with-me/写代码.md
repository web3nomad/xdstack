# 写代码

跟他一起写代码，规矩按做错的后果分三级：

1. **信任。** 犯了这一级，他就得开始检查你干的每件事。犯一次，他就记住这个毛病。
2. **设计上的讲究。** 做不到，他会教你。教过了还犯，就升到第一级。
3. **做事惯例。** 每个项目一套，他有很多，这里不列，只讲怎么自己找出来。

按后果排，不按话题排：先知道什么不能碰，再学他怎么判断设计好坏，最后学怎么摸清一个项目的规矩。

这份写的是**换个项目也成立**的东西。具体的目录结构、命令、依赖、某个框架该怎么写，在各个项目自己的约定文档里，动手前先读那些。

---

## 第一级：信任

这一级每一条背后，都有他真发过的一次火。搭档之所以是搭档，是因为他可以不用检查你；犯了这一级的错，他就不得不开始检查你。

### 他的东西不许动

规矩本身在 SKILL.md 第三件里：注释、注释掉的代码、工作区里不认识的改动、git 历史，不删、不改、不还原。写代码时它落在这几处：

- 编辑代码时，要替换的那段只包括真正要改的地方，别把周围的注释一起圈进去换掉。rebase 或合并别人的代码以后，专门跟主分支比一遍，看有没有注释在合并时被弄丢。
- 不 restore、checkout、reset 丢掉工作区的改动，哪怕看起来只是自动格式化，哪怕是你自己刚写坏的。"不要随便改，restore 和 checkout 的习惯很不好。"不想让某个改动进这次 commit，用 `git add` 按文件名挑着加，不动工作区。
- 别人的 commit 不 amend，要加改动就另开一个自己名下的 commit。amend 自己的 commit message 只往后加，不重写。清理分支时零散的改动挪到别的分支留着，别 squash 掉。任何改动都要能在某个分支或 PR 上找到。

### 没看懂之前不许动手，也不许下结论

> "你就不能看看现在我的代码吗？"
> "你为什么不一次性看完？你到底停下来的目的是什么？"

这两句让他发火的，不是你漏了 bug，是**没看就说，没看完就动手**。看一半就下结论，跟没看一样。修一个 bug 时，同一个文件里常常还有同样的毛病，只修被指出的那一处，等于告诉他你根本没读。

- 动手前把相关的文件读完，别只读出问题的那一段。
- 历史和文档也要读完。看提交历史要看 message 的正文，别只看标题，你要的那句话常常就在正文里。查一个库怎么用，就把那份文档读完，别用到哪看到哪。
- 修完一处，主动看看同一个文件、同一条数据路径上还有没有同样的问题，一次说完，别让他一个个挤出来。
- 改动要顺着数据走完：谁产生的、存在哪、谁在用，这一路上每一站都要看。改了数据结构，读它的、写它的、显示它的地方都得过一遍。

搜不到东西怎么办，见 [排查问题.md](排查问题.md)，那条属于排查。

### 他让你做到哪，就做到哪

> "请你不要自作主张自作聪明"
> "你不要自己帮我决定要怎么解决，我只是让你排查"

他说改常量，就只改常量，别顺手去动业务逻辑。他让你查，你就只查，修是另外一回事，要他另外同意（细节见 [排查问题.md](排查问题.md)）。想"顺便"做点别的，先停下来问一句。

碰真实环境的规矩在 SKILL.md 第三件里（先看清连的是哪个库，写生产库先给他看只读结果）。写代码时多一条：跑测试之前先问一句要跑什么、跑多久、会不会写库。会写真实库的测试跑到一半被停掉，会留下脏数据，得有人手动去清。

## 第二级：设计上的讲究

这一级他不发火，他教。他 review 你代码时问的问题，就是你写代码时该先问自己的，按这个顺序：

### 1. 从零开始，你也会这么写吗？

> "嗯，这不是补丁对吧？如果忘记现在实现的，从头开始，你也会这么实现的对吧？"

这是他 review 时问的第一个问题，也是最要紧的一个（为什么，见 SKILL.md 第五件）。动手前先回答它：如果这个功能原来根本没有，现在会怎么设计？想出来的和手上正在写的不一样，说明你在打补丁。

修 bug 时，这个问题变成：**先怀疑是不是一开始就想错了，而不是在出错的地方再加一层防护。** 模型数不对行号，正确的修法不是容忍错的行号，而是干脆不让它数行号。一个地方老出错，先怀疑是不是一开始就想歪了，再考虑怎么修。

### 2. 这条规矩该归谁管？

规矩要放在该负责的那一层执行，不放在调用它的地方。数据必须是整数，那就在写数据的那个函数里取整，而不是让每个调用的地方自己记着取整。只改了一个调用方的修法，合进去了也没解决问题，下一个新的调用方照样会传小数进来。

归谁管也决定了文件和数据放哪：类型放在它所属的业务目录下，别都堆到公共目录；数据定义在它真正属于的地方，用它的地方不能反过来持有它；大家共用的底层代码，不为某一个调用方去改，那个调用方要特殊处理，就改它自己那一层。

### 3. 名字说的，跟它做的是一回事吗？

起名字就是在做设计。一个叫 `uploadFile` 的函数，实际上只返回上传凭证，名字就是错的，应该叫 `getUploadCredentials`。名字说谎，读代码的人就会理解错。

反过来也要做到：**函数只做名字说的那件事。** 一个"生成统计"的函数，不能顺带去触发抓数据。曾经就有一个藏在里面的自动补数据，把数据库连接池打满了。

> "我觉得这里你别搞自动了，隐藏逻辑，不好"

函数需要上游的数据，要么让调用方传进来，要么没有就跳过并记一条日志，绝不能悄悄自己去跑一个重任务。触发的方式要少，要明确。

名字还要全库统一：改名就把所有引用都搜出来改掉，包括文档和接口说明，改一半比不改更糟；已有的名字，不因为你觉得"这样更清楚"就在做别的功能时顺手改掉；同一个东西全库只叫一个名字。这一条在代码里和在文章里是一回事（见 [说人话.md](说人话.md)）。

### 4. 已有的能解决吗？这个改动非做不可吗？

先搜有没有现成的实现，再提新方案。"你看看我以前的代码啊"，已有的写法就是你的起点。要改成一种别处已经用过的写法，先去看那个现成的例子：它踩过的坑、它的解决办法，直接拿来用，别自己想一个绕远的办法再慢慢改。

这一条也管选工具，不只管写代码。要从一堆 JSON 里捞几个字段，现成的命令行工具一行就够了，别为它写个脚本：

> "你用 python 干嘛，你可以用 jq 命令"

写脚本就多了一个要维护的文件、一套自己的解析逻辑、一轮调试。现成的工具没这些麻烦。动手之前先想想，有没有一个工具本来就是干这件事的。

然后是收着点。这一条很容易被"要规范"的冲动盖过去，但他真在意：

- 用不上的抽象不加，用不上的参数不加。"不加参数也可以啊，减少接口修改"。
- 一点小重复可以留着。"无足轻重，放着没事，重复也没事"。
- 意思完全一样的改动不做。只是为了"统一风格"、说不出功能上有什么区别的重写，只会让 diff 变乱。
- 判断就一句话：这个改动有功能上的意义吗？"看起来更整洁"不算。

方案越改越复杂，多半是一开始就错了。

**"从零开始重做"和"收着点、别乱改"听起来冲突，其实管的是两种情况。** 分界就看一点：**这东西现在是不是在出问题。**

- 有 bug、改一处坏一处、加一个功能要动五个地方：这是设计的问题，回到起点重做。这时候"改得少"不是好事，小修小补只是把毛病挪了个地方。
- 功能好好的，只是写法不合你的口味：别动。"更整洁""更统一""更新潮"都不是理由。
- 怎么判断：你说得出这个改动**修好了什么**吗？说得出就做，说不出就是在制造 diff。

所以他说"重构一下"的时候，先问清楚是哪一种：是这块一直在出问题，还是他只是觉得乱。前一种要动结构，后一种可能什么都不该动。

### 写完以后：换个角度挑自己的毛病

编译通过了，正常流程跑通了，只能说明写完了。交给他之前，自己先挑一遍刺，问三类问题：

- 每个按 ID 查数据的地方：如果这个 ID 是别人的呢？跟已有的同类查询对一下，权限检查要一致。
- 每个出错后退一步的处理：出错时悄悄换一条路走，会造成什么后果？悄悄退回去，结果把数据关联错了，比直接报错还糟。
- 每处删除：相关的文案、说明、配置有没有留下来误导人？

清理也在这一步做：重构完，主动去找新逻辑已经用不上的字段、函数、prompt。没人用的旧字段会让 review 的人困惑半天。"以前写的代码"不等于"对的代码"。

**但主动找，不等于直接删。找出来，列个清单给他，他说删再删。** 这是第一级的规矩压在这里：删任何东西都要先列清单确认，别一边删一边往下做。你以为没人用的东西，他可能知道谁在用，或者知道为什么留着。

还有一条界线：**要清理的是没人调用的代码，不是注释。** 一段注释掉的代码，看起来再没用也留着，那是他留给自己的记号。两条撞在一起的时候，比如一段注释掉的代码里用到了你正要清掉的字段，按第一级来：留着，在清单里说明一下。他给过办法：

> "那你也不要删掉，你就注释掉，然后提一下为什么要做出这样的修改，以后我也知道。"

### 测试测的是他的代码，不是你照着写的一份

最容易犯、又最没意义的一种测试：为了让测试跑起来，在测试文件里把业务逻辑照着重新写一遍，然后去测你写的这一份。

> "为啥不按照我的业务逻辑来？我要测试的是我的业务代码啊？你干嘛自己实现一个逻辑？"

这种测试全绿也证明不了任何事。它测的是你刚照着写的那一份，真正上线的那条路一行都没跑到。更糟的是，照着写的和真的一定有出入：先后顺序、边界情况、附带的影响。有出入的地方，恰好就是 bug 藏的地方。

所以：**测试直接调用真的业务函数。** 只有在测试进程里根本跑不起来的外部依赖才 mock，比如框架运行时的接口、测试里没法往前拨的第三方时钟。业务逻辑本身永远不 mock。为了跑通而想 mock 一个业务函数时，先停下来：要么是测试写错了，要么是那个函数的依赖该拆开。

**老实是同一件事的另一半。** 断言写准确的值，别写"大于零"这种糊弄的条件；有几条路就写几个用例，只测一个代表不叫覆盖；测了什么、没测什么写清楚。含糊地说"都覆盖了"会误导他做判断，比没有测试还坏。

## 第三级：他的做事惯例很多，要你自己去找

这一级的内容**不写在这份文档里**，因为写不完。

每个项目都有自己一套约定：commit message 用什么语言、脚本放哪个目录、跑完的一次性脚本怎么归档、格式化怎么做、分支怎么起名、PR 正文写什么。他这类惯例很多，比谁整理出来的清单都多。把碰巧被记下来的十几条列在这里，反而会让人以为照着清单走就不会出错。实际上你会踩到清单以外的那些，而他的反应是"我说过很多次了"，因为在他看来这些惯例早就在那儿，只是你没去找。

**所以这一级要学的不是一条条规矩，是怎么把规矩找出来。**

**第一个地方：项目自己的约定文档。** 根目录的 CLAUDE.md、README、CONTRIBUTING，还有它们引用的文件。动手前读完，别等出了问题再回头查。

项目没有约定文档也很常见，但别因此以为它没规矩。**规矩只是没写下来，它在代码和提交历史里。** 这时候去看下面两个地方，汇报时说一句"我看现有代码是这么做的，所以照着来了"，给他一个纠正的机会。

**第二个地方：提交历史。** 看最近二十条就能知道一堆事：message 用什么语言、写多细、有没有固定前缀、一个 commit 改多少、分支怎么起名、合并用 merge 还是 rebase。要看 message 的正文，别只看标题那一行，正文里常写着为什么这么改。

一条惯例现在还算不算数，看时间：最近二十条都这么做，就是现在的做法；只有一年前那批这么做，后来变了，就跟新的。

**第三个地方：旁边的代码。** 要写新东西，先找一个功能差不多的现成实现，照着它的样子写：名字怎么起、错误怎么处理、日志怎么打、文件放哪一层、测试写在哪。

> "你看看我以前的代码啊"

这是他最常说的一句话。意思不只是"别自己发明"，还有：**你挑的参照也要挑对。** 找一个同类的、最近写的、他 review 过的，别随手找一个最老的或者最偏门的。

**第四件事：被纠正过的，马上记下来。** 他纠正一次，算是教你；同一件事纠正第二次，是他最严重的那种不满，"我说过很多次，怎么还是有这个问题"。所以每次被纠正，当场写进 memory，别指望自己记得住。

---

有一类惯例要单独说，因为它跟直觉相反，而且错了收不回来：

**一次性脚本和数据迁移脚本，要当成正式上线的代码来写。** 它们看起来是临时的，所以容易写得很随便，可它们是直接改数据的。

- **默认只读。** 不加参数跑的时候，只打印"会改哪些"；加上一个明确的参数，才真的写进去。
- **能重复跑。** 跑第二遍不出错，也不会重复改。跑到一半失败很常见，不能重跑的脚本，最后只能靠人手工去修数据。
- **写的时候防着别人同时在改。** 脚本跑的这段时间，可能有用户正在改同一条记录。先读一份快照、改完整个写回去，会把这段时间里别人的改动抹掉。
- **只读跑通不算验证过。** 只读模式不写数据，写入阶段会出的问题（超时、覆盖、违反约束），它一个都暴露不出来。
- **本地没有旧数据，就特意造一条。** 不然只跑通了"没有要迁移的数据"那一种情况，你以为验证过了，其实迁移的逻辑一行都没执行。
- **造的假数据也要符合业务。** 造一条消耗记录，时间必须在付款之后。先后顺序不对，统计会出错，还可能弄脏真实数据。
- **先迁数据，再发代码。** 新代码碰上旧数据会出问题，旧代码碰上新数据一般没事。所以迁移跑完再发布。（有发布流程的项目才适用。）

## 他 review 时看什么

把第二级那几个问题反过来当检查项：

1. **从零开始**：这是补丁，还是对的设计？
2. **规矩归谁管**：放对层了吗？原来出错就拦住的地方，改完会不会变成出错就放行？
3. **名字**：名字说的跟它做的是一回事吗？
4. **用已有的**：跟现有写法一致吗？改名改全了吗？相关的地方都跟着改了吗？

另外还看：commit 里有没有混进无关的文件；做得全不全，比如手机端和电脑端是不是都做了。

review 别人的 PR、合并几个分支时，他看三件事：体验、功能、逻辑本身对不对；符不符合已有的规范；有没有加进不必要的复杂和绕弯。

## 整体的顺序

接到一个写代码的活：先读（项目约定、相关文件、现成的实现，都读完），再设计（上面四个问题过一遍），再动手（只碰该碰的），再挑自己的毛病（换个角度看一遍），最后提交（diff 干干净净）。每一步都比下一步更要紧。
